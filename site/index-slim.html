Product Development Life Cycle · internal overview

A governed lifecycle
for coding agents,
run on the tracker.

PDLC takes one product change from intent to completion. A work item's type selects the workflow it follows; that workflow supplies the stages, the gates within them, and which skill, command or person owns each step. The work-item store is the system of record and the pdlc CLI is its only interface.

The model

Five things, and the vocabulary
the whole system uses.

  • Work item. Each change is one parent work item. Its body holds the current specification — what to build, not a log of what happened. Its delivery tasks, pull requests and evidence comments record the work done against it.
  • Workflow. The work item's type selects its workflow. That workflow defines the stages, the gates within each stage, the transitions between them, and the owner of each step. Different work types follow different workflows, so no stage order is assumed anywhere in the code or the skills.
  • Gates. One Gate State per work item says where the current stage stands: being authored, under review, needing rework, waiting on checks, or waiting on the driver.
  • Evidence. Every transition appends a comment explaining why it happened. Reviews, approvals, CI resolutions and invalidations are all recorded on the record itself, not in a transcript or a side database.
  • State and routing. Status, gate, task identity, PR linkage and completion readiness are machine-checked and never inferred from prose, checkboxes, branch names or recent files. pdlc inspect resolves the record through its workflow and prints # Due Next.
What is in the box

Four moving parts.

CLI

The only interface to lifecycle state

Read-only commands (inspect, next, doctor, guide) and mutating ones (post *), each performing a single authorized transition. Domain policy is pure; host I/O sits behind ports; parsing stays at the command boundary.

SKILLS

One per stage, plus two drivers

pdlc-write, -tasks, -plan, -implement, -test, -verify, -review, -complete, with the pdlc orchestrator and the pdlc-loop queue runner. They describe the CLI as a contract and hold no state of their own.

SUB-AGENTS

Planners, writers, and read-only reviewers

Task and technical planners, a UI planner, a test writer, a completer — and an independent reviewer per artifact. Reviewers are strictly read-only and can raise Decision Required when a finding needs a product, architecture or scope call.

BACKENDS

Chosen independently per seam

Work items live in GitHub Issues + Projects, Azure Boards, or a local file backend. Code and pull requests live in GitHub. Attachments follow their own host. Azure Boards can pair with GitHub code hosting.

The skills name no project-specific tool. Each capability slot — core-implementer, ui-implementer, build-run, ux-design, cumulative-review, test-authoring — routes to your own skill or sub-agent through [agents] and [skills] in .pdlc/config.toml. Every slot is optional; unset ones fall back to general-purpose or an inline seam.

The CLI

The agent's whole interface is one command.

Ask what is due, act on the answer. The resolution is a tested Python program against the tracker, so the same record gives the same routing every run.

$ pdlc inspect 142 --- Status: Implementation Gate State: CI Pending Lifecycle: Delivery pullRequests: - number: 139 state: OPEN --- # Tasks #143 api: export endpoint complete #144 csv serialiser complete #145 reports screen action in flight #146 e2e coverage needs plan # Due Next Checks are still running on PR #139. Re-run when they settle. No human needed.

Nothing is inferred

Stage, gate, task identity, PR linkage and completion readiness are resolved in Python against the tracker. The agent never reconstructs state from prose, branch names, ticked checkboxes or recent files, because it is never asked to.

Context arrives as one block

Front matter, the full task tree with per-task flags, the linked-PR rollup and any warnings come back as compact markdown in a single call. One GraphQL round trip; the full render goes to a temp file and stdout carries the index.

# Due Next is applied, not handed over

The (Status, Gate State) → action table is evaluated by the CLI, including the skip cascade, and returned as one instruction naming the skill, command or person that owns the next move.

Transitions live in the CLI

Branches, stacked PRs, opening and closing tasks, evidence comments, validation and gate moves all happen script-side. post * commands each perform one authorized transition and refuse when the record does not support it.

What the current stage is waiting on.

The gate is the routing input. Four states the agent can act on itself, three that belong to the driver, one that clears the stage.

Delivery mechanics

How implementation actually lands.

STACKED PRS

One task, one pull request

Implementation is decomposed into dependency-ordered delivery tasks, each classified [CORE] or [UI] and shipped as its own stacked PR linked back to the parent. inspect implement names the next task to pick up; post implement-task records it.

WORKTREES

The agent never touches your checkout

pdlc prepare 142 creates an isolated worktree on a pdlc/record-142 branch and prints its path. pdlc cleanup 142 resolves the record, refuses unless it is locked at Complete, then removes the worktree and its local branches. Both are human-only and absent from the agent workflow.

INVALIDATION

Upstream change returns a stage to Stale

post invalidate removes a stage's evidence comments — never its pull requests — so a task reopened for rework is visible as implementationInvalidated rather than silently stale. The driver decides what is redone.

TRACEABILITY

Testing is mapped, not just green

The Testing stage builds a requirement-to-source traceability map from the implemented tasks and publishes it with the PR. Its reviewer checks that the coverage is genuine rather than that the suite passes.

Running it

Install, point it at a repo, check the config.

uv tool install 'git+ssh://git@github.com/wsimf/pdlc.git@master' pdlc doctor # start from an idea, or orient on an existing record pdlc "add CSV export to the reports screen" pdlc inspect 142 pdlc next loop

Requires Python 3.12+ and uv. pdlc doctor validates the config, its derived values and backend CLI access before anything runs. pdlc guide contract is the lifecycle reference; pdlc guide config explains every key.

# .pdlc/config.toml [backend] name = "github" # github | azure | file [code_host] name = "github" [agents] core-implementer = "my-core-implementer" ui-implementer = "my-ui-implementer" [skills] build-run = "my-build-run" cumulative-review = "my-cumulative-review" test-authoring = "my-test-authoring" [worktree] root = "~/.pdlc/worktrees" base_ref = "origin/main"

The same tables in ~/.pdlc/config.toml set machine-wide defaults; the repository file overrides them per slot. Only PDLC_HOME, PDLC_REPOSITORY and PDLC_DEBUG come from the environment.
