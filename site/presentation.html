Building the lever: things I learnt building with coding agents.

Set expectations: this isn't a product pitch. It's what I learnt, including what I got wrong, and you can use all of it with whatever tools you have.
The idea

What’s the lever?

“Give me a lever long enough and a place to stand, and I will move the world.”Attributed to Archimedes

How I’ve come to think about it: the agent is the force, and the lever is what you build around it. The tools, checks, and records that let a little effort go a long way.

For me, building levers helped more than writing better prompts.

Draft definition: put this in your own words. The point is that pushing harder on the agent (more prompts, more agents) gives less than making each push go further.
What changed

Faster code raised harder questions.

Can I trust it?

  • It marks its own homeworkThe author also says it’s fine.
  • Hidden assumptionsDecisions get buried in the diff.
  • “Done” is a guessNothing proves it’s finished.

Can I keep up?

  • Too much to reviewDiffs arrive faster than anyone can read them.
  • Agents collideParallel work in one checkout gets in the way.
  • Specs driftRequirements change and the plan and code don’t follow.

Can the team rely on it?

  • Invisible workProgress is stuck in one person’s terminal.
  • No memory“Why did we build it this way?” dies with the chat.
  • Tool lock-inThe way of working is tied to one agent or tracker.

Down the rabbit hole

Each fix led one level deeper.

  1. Better prompts

    Re-explaining the same context every session.

  2. Written skills

    Reusable instructions. Agents followed them… mostly.

  3. A tool

    I asked the agent to build a CLI that checks the facts instead of guessing them.

  4. A workflow

    Stages, reviews, and approvals, recorded on the board.

  5. Tools for the tool

    Tests, retries, and recovery, so it holds up when nobody’s watching.

What helped me most

Instead of asking the agent to do it, I asked it to build a tool.

  • Same answer every time

    A script runs the same way each time. My prompts never quite did.

  • Testable

    I could write tests for a tool. I couldn’t test “please remember to”.

  • Saves context

    The agent could spend its context on the actual problem instead of rediscovering the routine.

  • Reviewed once

    I review the tool once, rather than checking every run.

My rough rule now: if I’ve asked for it twice, it might be worth a tool.

This is the core of the talk. The agent is great at writing small, boring tools, and those tools are where the leverage is.
An example

“What’s next on this work item?”

Asking the agent

skills/work-on-pbi/SKILL.md 
---
name: work-on-pbi
description: Use when asked to continue a PBI
---
# Work on a PBI

## 1. Authenticate
Export the PAT so az can reach the board:
export AZURE_DEVOPS_EXT_PAT=…
az devops configure --defaults \
  organization=… project=…
If this fails, ask the user to sign in and stop.

## 2. Find the PBI
az boards work-item show --id 3054301
Check it’s a Product Backlog Item. If it’s a
Bug or a Task, find its parent first, unless…

## 3. Read the description and comments
Read System.Description and the acceptance
criteria. Then fetch every comment:
az devops invoke --area wit \
  --resource comments …
Ignore bot comments, unless they mention CI.
Newer comments override older ones.

## 4. Check GitHub
gh pr list --search "AB#3054301" --state all
For each PR:
gh pr checks <number>
gh pr view <number> --comments
If CI is failing, fix that first, unless the
failure is unrelated, in which case…

## 5. Work out what’s next
If the description changed since the plan was
written, re-plan before coding, unless…
If a reviewer asked for changes, do those first.
If everything is merged, update the PBI state
and remember to add a comment saying…

## 6. Before you finish
Don’t forget to move the card on the board.
Don’t forget to link the PR to the PBI.
…

Every session, the agent reads all of this, runs each step, and decides a little differently.

Same idea, applied to instructions

A huge skill file became a single command.

One massive skill file

## Before you start
1. Read the issue and all of its comments
2. Find the linked PRs and check their CI
3. If CI is failing, fix that first, unless…
4. If the plan changed since last time, then…
5. Work out which task is next. Skip any that…
6. Remember to check for open review comments
7. Don’t forget to update the board when…
8. If a decision is needed, stop and…
9. …

The agent reads it all, interprets it, and still gets it slightly different each run.

One command

$ pdlc inspect implement 3054301
whether work is due
which mode it’s in
the one task to work on next

The skill shrank to: run this, then do what it says. The tool gathers the context, so the agent’s context stays free for the work.

Same lesson as the last two slides, applied to agent instructions. The long file was me hoping the agent would follow a procedure; the command just does the procedure and hands over the result.
What trust took, for me

I could only walk away from work I could trust.

  • A record outside the chat

    Requirements, decisions, and progress survive any session and any agent.

  • A known next step

    Work is routed by state, so nobody has to prompt the next move.

  • “Done” you can trust

    An independent reviewer checks the work against the requirement, with evidence.

  • A rule for interrupting me

    Agents stop for real decisions and approvals, and for nothing else.

Each of these is a lever. None of them needs a particular tool: a doc, a script, or a second agent can do it.

Other things I learnt

A few things I learnt the hard way.

  • Prose drifts. State doesn’t.

    I ended up turning anything a later step depends on into checked data, rather than a sentence for an agent to interpret.

  • Handing over the context

    Agents gathering their own context gave me different results each time. Building their brief made every run start from the same scope.

  • Nobody’s watching when it fails

    Unattended work needed safe retries and clear recovery steps, not a stack trace.

  • One source of truth

    Copying a tool’s --help into instructions went stale fast. Pointing at it worked better.

If any of this resonates

Some things you might try.

  • Turning repeats into tools

    Next time you ask for the same thing twice, see whether a small tool could do it.

  • Keeping context out of the chat

    Somewhere that outlives the session, so you’re not repeating yourself.

  • Agreeing on “done” first

    Deciding how you’ll know it’s right before an agent starts.

  • A separate reviewer

    A fresh agent checking the work against the requirement, rather than its own summary.
