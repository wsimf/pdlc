Notes from down the rabbit hole

From taking turns
to working apart.

How I got my agents working on their own, safely, with the right mix of skills and code. What I tried, what stuck, and what didn't.

Hi everyone, thanks for coming. If we haven't worked together, I'm Sudara, I'm on the Flex team. So, like most of you, I use coding agents every day. And for a long time I used them the same way. I'd write a prompt. It'd do something. I'd read it, then prompt again. It's basically taking turns. It's working, I'm waiting. I'm thinking, it's waiting. And that's fine, it works. But the agent only goes as fast as I do. And honestly, two of those at once is about my limit. So I tried to get out of that loop. Plan mode first. Agree the plan, let it run. Less back and forth, which was great. But it'd tell me it was done, and it wasn't. Or it was done, just not what I wanted. Then cloud agents. Now it's running without me, nice. But I couldn't really see what it was doing. And I wasn't comfortable putting my name on that. To be clear, I still use all of these. Every day. But it got me wondering. What would it actually take to trust an agent with work I'm not watching?

TL;DR

  • Prompting alone keeps work synchronous

    Each step waits on a new prompt, so the agent progresses only as fast as I respond.

  • Combining skills and code works best

    Skills provide judgement and code enforces the process. Together they let agents work independently and safely.

  • How I arrived here

    The steps I took, the problems each one solved, and the mistakes along the way.

So, short version first. If I want to leave an agent alone, two things have to be true. It can't be waiting on me for every step. And by the time it comes back to me, it's already been checked. Tested. Reviewed by other agents. The small stuff already caught and fixed. So when it lands on my desk, I'm not starting the review from scratch. I'm fairly confident it's already close to what I actually wanted. Getting there took a while. Prompts on their own left too much to the agent. Same instructions, different run, slightly different result. It'd skip a step. Or tell me it was done when it wasn't. Scripts on their own went the other way. Too little. They're great at doing the same steps every time. But they can't make a judgement call. They can't read a requirement and work out what someone actually meant. What worked was the mix. Code for the process. Skills for the judgement. The rest of this is how I got there. What I tried, what broke, and what I'd do differently.

   Don't build a new Button if…

5. Add unit tests for every new…

8. Run the tests. If one fails…
9. Open a PR. Link the ticket.
10. If CI fails, read the log and…
11. Ask a reviewer agent to check…
12. If it asks for changes, then…

👍 Liked

  • Written once.No more retyping. Every session starts from the same instructions.
  • The agent does the checks.Tests, diff and review happen without me asking.
  • Shareable.Teammates and other agents get the same playbook.
  • Cheap to start.It’s just Markdown. Nothing to build.

👎 Disliked

  • “Mostly” followed.The agent decides what it means every run. Same skill, different result.
  • It only grows.Every failure adds another “if… unless…”, and the key lines get buried.
  • There’s no state.Each session asks “which task? did the tests pass?”, and someone has to answer.
  • “What’s next?” is still on you.One skill, one job. Picking the next one is still re-prompting.
  • You can’t prove it did it.No evidence, just “I ran the tests”. So you check anyway.
  • It costs context.Every word is read every run, crowding out the actual code.
  • It’s hard to test.You can’t unit-test prose. You find out when a run goes wrong.

The idea

What’s the lever?

“Give me a lever long enough and a place to stand, and I will move the world.”Attributed to Archimedes

The agent is the force. The lever is what you build around it: the tools, checks, and records that make every push go further.

For me, building levers helped more than writing better prompts.

There's a line usually put down to Archimedes. Give me a lever long enough, and a place to stand, and I'll move the world. That's how I think about it now. The agent is the force. It's strong. It doesn't get tired. But I kept pushing harder on it. More prompts. More agents. And I got less and less back. The lever is what you build around it. The tools, the checks, the record of what's been done. The stuff that makes every push go further. For me, building levers helped way more than writing better prompts. What helped me most

Don’t let the agent fish bare-handed. Have it build a rod, and a skill to use it.

  • Same answer every time

    A script runs the same way each time. My prompts never quite did.

  • Testable, reviewed once

    I could test and review a tool once. I couldn’t test “please remember to”.

  • Saves context

    The agent could spend its context on the actual problem instead of rediscovering the routine.

  • A skill to use it

    The tool does the same thing every time. The skill tells the agent when to reach for it, and how.

My rough rule now: if I’ve asked for it twice, it might be worth a tool, and a skill to use it.

I saw a video a while back, and this line stuck with me. You can ask your agent to fish for you. Or you can ask it to build you a fishing rod. I'd take it one step further. Get it to build the rod. Then get it to write a skill on how to use it. The rod does the same thing every time. The skill knows when to cast, and where. The agent's still the one fishing. It's just not doing it with its bare hands anymore. And yeah, that's the mix from the start. Code for the process, skills for the judgement.

Other things I learnt

A few things I learnt the hard way.

  • Prose drifts. State doesn’t.

    I ended up turning anything a later step depends on into checked data, rather than a sentence for an agent to interpret.

  • Handing over the context

    Agents gathering their own context gave me different results each time. Building their brief made every run start from the same scope.

  • One source of truth

    Copying a tool’s --help into instructions went stale fast. Pointing at it worked better.
