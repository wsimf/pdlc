Notes from down the rabbit hole

From taking turns
to working apart.

How I got my agents working on their own, safely, with the right mix of skills and code. What I tried, what stuck, and what didn't.

Hi everyone, thanks for coming. If we haven't worked together, I'm Sudara, I'm on the Flex team. So, like most of you, I use coding agents every day. And for a long time I used them the same way. I'd write a prompt. It'd do something. I'd read it, then prompt again. It's basically like taking turns. When it is working, I'm waiting, and when I'm thinking, it's waiting. And that's fine, it works. But the agent only goes as fast as I do. And I felt I can only handle two or three of them at most at a time. So I tried to get out of that loop. Tried planning things first. We agree the plan, and let it run. Less back and forth, which was great. But the agent would tell me it was done, and with my expectations, I don't think it was. Or it was done, but not what I wanted. I still use these tools every day. But it got me wondering. What would it actually take to trust an agent with work I'm not watching?

TL;DR

  • Prompting alone keeps work synchronous

    Each step waits on a new prompt, so the agent progresses only as fast as I respond.

  • Combining skills and code works best

    Skills provide judgement and code enforces the process. Together they let agents work independently and safely.

  • How I arrived here

    The steps I took, the problems each one solved, and the mistakes along the way.

So, summary of the talk. If I want to leave an agent alone, two things have to be true. It can't be waiting on me for every step. And by the time it comes back to me, it should have already been checked. Tested. Reviewed by other agents. The small stuff should have been already caught and fixed. So when it lands on my desk, I'm not starting the review from scratch. And I need to be fairly confident it's already close to what I actually wanted. Getting there took a while. Prompts on their own left too much to the agent. Same instructions, different run, slightly different result. It'd skip a step. Or tell me it was done when it wasn't. Scripts on their own went the other way. Too little. They're great at doing the same steps every time. But they can't make a judgement call. They can't read a requirement and work out what someone actually meant. What worked was the mix. Code for the process. Skills for the judgement. The rest of this is how I got there. What I tried, what broke, and what I'd do differently.

one skill, growing

👍 Liked

  • Written once.No more retyping. Every session starts from the same instructions.
  • The agent does the checks.Tests, diff and review happen without me asking.
  • Shareable.Teammates and other agents get the same playbook.
  • Cheap to start.It’s just Markdown. Nothing to build.

👎 Disliked

  • “Mostly” followed.The agent decides what it means every run. Same skill, different result.
  • It only grows.Every failure adds another “if… unless…”, and the key lines get buried.
  • There’s no state.Each session asks “which task? did the tests pass?”, and someone has to answer.
  • “What’s next?” is still on you.One skill, one job. Picking the next one is still re-prompting.
  • You can’t prove it did it.No evidence, just “I ran the tests”. So you check anyway.
  • It costs context.Every word is read every run, crowding out the actual code.
  • It’s hard to test.You can’t unit-test prose. You find out when a run goes wrong.
I wrote it down. The whole workflow. Every step, every check, what to do when something fails. And I put it in a skill, so the agent reads it every single run. Other things I learnt

A few things I learnt the hard way.

  • Prose drifts. State doesn’t.

    I ended up turning anything a later step depends on into checked data, rather than a sentence for an agent to interpret.

  • Handing over the context

    Agents gathering their own context gave me different results each time. Building their brief made every run start from the same scope.

  • One source of truth

    Copying a tool’s --help into instructions went stale fast. Pointing at it worked better.

Before I finish, a few things I had to learn the hard way. First, prose drifts. State doesn't. Anything a later step depends on, I ended up turning into data the tool can check. Not a sentence an agent has to interpret. Second, hand over the context. When agents went and gathered their own, I got different results every time. When I built the brief for them, every run started from the same place. And third, keep one source of truth. I used to copy a tool's help text into my instructions, and it went stale really fast. Just pointing at the help worked much better. [Cards appear on load. Swap in your own "I thought X, then learned Y" if you have a sharper one.]

What’s next

Where it could go next.

  • Cheaper agents for decisions

    When a step needs a structured answer, hand it to an agent built for deciding, like Jev, instead of a lightweight LLM call.

  • Starting agents from code

    The CLI can say what’s next, but can’t start an agent. A GitHub Copilot SDK integration could run that step the same way every time.

  • Proactive, not reactive

    Feed in what’s happening, like production logs, user feedback and outside events, so workflows start on their own, not when I prompt.

  • More workflows

    Features are the only workflow today. Bugs and spikes need their own stages and gates.

One last thing. Where this could go next. First, decisions. A lot of steps just need a structured answer. Is this approved? Which option? Today I use a lightweight LLM for those. But there are agents built for exactly that now. Like Jev. Cheaper, and made for deciding. So I'd like to hand those steps over. Second, starting agents. The CLI can tell an agent what's next. Third, proactive, not reactive. Right now, nothing happens until I prompt. But what if the workflow was watching? Production logs, user feedback, things changing outside.
